# Design decision log

Each entry records the decision, the directive it serves (DD1–DD10, see TRACEABILITY.md), the alternatives
considered, and the reason. Entries dated 2026-10-05 were made while building the prototype from the
researcher's specification (`CLAUDE_CODE_PROMPT.md`) with Claude Code; see AI_USE.md.

| # | Date | Decision | Directive | Alternatives considered | Reason |
|---|---|---|---|---|---|
| 1 | 2026-10-05 | Engine is a pure, deterministic rule set: no randomness, clock or network; all ties broken alphabetically. | DD2, DD10 | ML ranking; random tie-breaks | Every rule is measured by an evaluation metric (Q2 needs identical repeat output); deterministic rules are testable and auditable. |
| 2 | 2026-10-05 | Similarity is Jaccard J(S,O)=\|S∩O\|/\|S∪O\| between recognised skills and each occupation's essential skills. | DD2 | Cosine on embeddings; raw overlap count | Specified; transparent and explainable ("you have 2 of 5 skills"); no external model. |
| 3 | 2026-10-05 | Nearest occupations = top K=3 by J, ties by occupation name A→Z (case-insensitive, then exact). | DD2 | K=1; K=5; tie by row order | Specified K; name order is stable regardless of CSV row order. |
| 4 | 2026-10-05 | Candidate score = mean J over the K nearest after adding the skill minus mean J before (adjacency gain); sort by gain desc, then skill A→Z. Primary = first; alternatives = next 3. | DD1, DD2, DD6 | Most frequent missing skill; target-occupation gap | Specified; picks the smallest step towards several nearby occupations at once. |
| 5 | 2026-10-05 | All similarity arithmetic uses exact fractions (`fractions.Fraction`). | DD2 | Floating point | Mathematically equal gains can differ in floating point, which would bypass the alphabetical tie-break. |
| 6 | 2026-10-05 | When fewer than K occupations overlap with the profile, zero-similarity occupations still fill the K slots (spec applied literally). **Correction (2026-10-05, real skill map):** an earlier note said such skills never rank first; that held only for the test fixture. With small profiles a skill from a zero-similarity occupation CAN rank first (e.g. 'statistics' alone gets an agricultural-science skill). | DD2 | Exclude J=0 occupations | Follows the specification exactly; raised with the researcher for a decision (see #34). |
| 7 | 2026-10-05 | Skill normalisation: lowercase, trim, collapse whitespace. Unknown skills are ignored and listed as "not recognised" in the explanation. | DD8 | Fuzzy matching; reject the profile | Specified; fuzzy matching would add hidden behaviour. |
| 8 | 2026-10-05 | Three fallbacks (empty profile, only unrecognised skills, saturated nearest occupations) return no recommendation and a clear explanation, never an exception. | DD8 | Raise errors; recommend from the whole map | Q4 edge-case robustness; a clear message preserves trust. |
| 9 | 2026-10-05 | Every explanation lists nearest occupations, skills held per occupation, the reason ("smallest step that brings you closest to…"), each source, and the disclaimer, including fallbacks. | DD8 | Short explanation only | Q3 explanation completeness; transparency of an AI suggestion. |
| 10 | 2026-10-05 | Income is computed after ranking and only for version A, from the first nearest occupation containing the recommended skill, labelled "Estimated … (literature-derived estimate, not financial advice)"; B always returns "". | DD9 | Income-weighted ranking; show income in both versions | Income must inform, not steer; A/B paired comparison isolates its effect on presentation only. |
| 11 | 2026-10-05 | Pathway: six modules, difficulty start, start, start+1, start+1, start+2, start+2 (cap 5); start = 1/2/3 for limited/foundational/moderate; unknown level = foundational. | DD3, DD4 | Fixed difficulty; per-module jumps of 2 | E2 graduated difficulty (zone of proximal development): never more than one level per step. |
| 12 | 2026-10-05 | Estimated minutes per module = 5 + (difficulty − 1), i.e. 5–9 minutes. | DD4 | Fixed 10 minutes | Keeps every unit within 5–10 minutes while reflecting difficulty; display only. |
| 13 | 2026-10-05 | Progress: milestone MSn every 3rd pass; difficulty +1 after every 2nd pass (cap 5); a pass resets consecutive fails. | DD5, DD3 | Milestone per module; per-pathway only | E1: six passes give exactly two milestones; staging builds confidence. |
| 14 | 2026-10-05 | Revision on the 2nd consecutive failure only: difficulty −1 (floor 1), fails reset; message says an easier step was added and why, without "you failed" language. | DD3 | Revise on first fail; no revision | Q1 adaptive revision; competence-protecting framing (self-efficacy). |
| 15 | 2026-10-05 | Nudge when days inactive ≥ 2, at most one per day, with text tied to the next milestone ("You're N short modules away from MSn"). | DD7 | Daily reminders; generic text | Q5; Fogg trigger logic links the prompt to a near, concrete goal. |
| 16 | 2026-10-05 | In the app, the nudge is checked when the app opens, before `session_start` records activity, and shown as an in-app banner; `notification_opened` is logged when tapped. | DD7, DD10 | Push notifications | No push service or third-party provider needed (POPIA, local only); the rule itself is unchanged. |
| 17 | 2026-10-05 | Engine never reads `target_occupation`, `acceptable_recommendations`, `designed_to_test`, `employment_goal`, `is_edge_case`; extra keys are ignored. A test fails if any is even accessed. | DD10 | Trust callers | Oracle isolation: outputs cannot be influenced by expected answers. |
| 18 | 2026-10-05 | A skill map with a duplicate occupation name raises a clear error at load time. | DD10 | Merge rows; keep the last | Data integrity of the research instrument; silent merging would change results. |
| 19 | 2026-10-05 | `skillpath_adapter.SkillPathEngine` returns only the harness contract keys; the engine also returns display keys (status, nearest occupations, sources, minutes) used by the API. | DD8, DD10 | One shape everywhere | Keeps the harness contract exact while giving the app the full explanation. |
| 20 | 2026-10-05 | A/B arm: A if the SHA-256 of the user ID (as an integer) is even, else B; researcher override `?arm=`. Implemented in `skillpath/assignment.py`, not the API. | DD9, DD10 | Random assignment; alternating | Deterministic and reproducible; API holds no decision logic. |
| 21 | 2026-10-05 | A user is created only when consent and 18+ are both confirmed; consent timestamp stored; no name, email or phone collected; qualification and discipline are not collected by the app (the engine does not use them). | DD10 (ethics) | Optional consent; collect demographics | POPIA data minimisation and ethics approval. |
| 22 | 2026-10-05 | Added event type `pathway_deferred` (not in the original list) for "Not now". | DD6, DD10 | Log nothing; reuse another type | Otherwise autonomy choices to defer would be unmeasurable. Flagged to the researcher. |
| 23 | 2026-10-05 | Server logs decision events (onboarding_complete, assessment_complete, pathway_*, module_complete, milestone_reached, roadmap_revised, notification_sent); the app may only report session_start, session_end, assessment_started, notification_opened. | DD10 | Client logs everything | Decision events cannot be spoofed by the client and match engine outputs exactly. |
| 24 | 2026-10-05 | Module results are accepted only for the current module, in order. | DD3, DD5 | Any order | Keeps progress state consistent with the six-step graduated sequence. |
| 25 | 2026-10-05 | `DELETE /users/{id}` removes the user's events as well as profile and pathway. | DD10 (POPIA) | Keep anonymised events | Specified ("every row"); right to deletion over retention. Deleted users' events are absent from the export. |
| 26 | 2026-10-05 | Admin export protected by a token in local `.env`; disabled (503) when no token is set; constant-time comparison. | DD10 | No protection; user accounts | No secrets in the repo; simple local control. |
| 27 | 2026-10-05 | CORS allows any origin. | — | Restrict to localhost | Local prototype accessed from Expo web and phones on the LAN; no cookies or credentials are used. |
| 28 | 2026-10-05 | App built with Expo (React Native + TypeScript) using simple state-based navigation (no router), core components only, no images beyond defaults. | DD4, DD5 | Expo Router; web-only React | Runs in Expo Go and the browser with minimal dependencies and low data use. |
